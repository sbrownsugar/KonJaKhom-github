## 2. เป้าหมายจำนวนตัวอย่าง (ล็อกก่อนเก็บ)

**n = 50 คน ที่ใช้ได้จริง** (ตอบแบบสอบถามครบ + ภาพผ่านการตรวจคุณภาพ)

- คาดว่าข้อมูลใช้ไม่ได้ ~25% (ผมบังหู, เบลอ, รหัสไม่ตรง, ตอบไม่ครบ) → **ต้องเก็บผ่านบูธ ~65 คน**
- **พื้นขั้นต่ำ: ถ้าได้ < 35 คน → เปลี่ยนกรอบเป็น "การศึกษานำร่อง (feasibility study)" ทันที**
  (ตัดสินใจข้อนี้ **ตอนนี้** ก่อนเห็นผลโมเดล ไม่ใช่ตอนผลออกมาไม่สวย)
- **แบบสอบถามอย่างเดียว (ไม่มีภาพ): เก็บให้ได้มากที่สุด เป้า 100+**
  ใช้เพื่อ (ก) นิยาม "ค่าเฉลี่ย" ของโรงเรียน (ข) สอบเทียบระดับฐานของสมการ

## 3. ตัวแปรผลลัพธ์ (Outcome) — ล็อกแล้ว

### PRIMARY: `NRS_max` = ระดับอาการที่รุนแรงที่สุดใน 7 วัน (สเกล 0–10, ต่อเนื่อง)

**เหตุผลที่ไม่ใช้ "ปวด/ไม่ปวด":**
เราจำลองสถานการณ์ 400 รอบต่อขนาดตัวอย่าง (สคริปต์: `analysis/power_sweep.py`) พบว่า:

| n | ใช้ label "ปวด/ไม่ปวด" | ใช้ label "ระดับ 0–10" |
|---|---|---|
| 25 | **47%** (เท่าโยนหัวก้อย) | **89%** |
| 50 | 74% | **100%** |

การบีบตัวแปรต่อเนื่องให้เป็นสองค่า **ทิ้งพลังทางสถิติไป ~36–40% ฟรีๆ**

### ⚠️ แผนสำรองที่ประกาศไว้ล่วงหน้า
**ถ้าสัดส่วนคนที่ตอบ NRS = 0 เกิน 40%** → เปลี่ยน PRIMARY เป็น **Spearman correlation / ordinal regression**
(ตัดสินจากค่าเดียวนี้เท่านั้น **ไม่ใช่จากการดูว่าวิธีไหนให้ p สวยกว่า**)

### 📌 การแก้แผน ครั้งที่ 2 — **16 ก.ค. 2569 (ยังไม่มีข้อมูลแม้แต่แถวเดียว · n = 0)**

> **แก้:** ตัวเลข power ในตารางด้านบน (n=25 → 89%) เป็นค่าที่ **มองโลกในแง่ดีเกินจริง**
>
> **เหตุผล:** เราตรวจสอบ `analysis/power_sweep.py` (ตัวที่ให้เลข 89%) แล้วพบว่ามัน
> **แอบปลูก "ผลของท่าทาง" และ "ปฏิสัมพันธ์ ท่าทาง×ภาระ" ไว้ในข้อมูลจำลอง** ซึ่ง
> **ขัดกับข้อค้นพบหลักของเราเองที่ว่าท่าทางมีน้ำหนัก 0** (ดู §1) การปลูกสัญญาณที่เราเชื่อว่าไม่มีจริง
> ทำให้ power ดูสูงเกินความเป็นจริง
>
> **สิ่งที่ทำใหม่ (ยังไม่เห็นข้อมูล):** เขียน `analysis/power_compare.py` + `power_lambda_sensitivity.py`
> จำลองแบบ **อิงความชุกคนไทยจริง + β จากงานวิจัย + ตั้งท่าทาง β=0** พบว่า:
>
> | | ต้องใช้ n (power ≥ 80%) |
> |---|---|
> | label ระดับ 0–10 (NRS) | **n ≈ 40–50** (ที่ n=25 ได้เพียง ~35%) |
> | label ปวด/ไม่ปวด (binary) | มากกว่า 70 (ที่ n=25 เหลือ ~1%) |
>
> **ผลที่ตามมา:**
> 1. **เป้า n = 50 ที่ล็อกไว้ใน §2 ยังถูกต้อง** — การแก้นี้ *สนับสนุน* การตัดสินใจเดิม ไม่ได้ล้มมัน
> 2. ข้อสรุปเชิงคุณภาพ "NRS ดีกว่า binary มาก" **แข็งขึ้น** (ช่องว่างกว้างกว่าเดิม)
> 3. **ห้ามพูด "89% ที่ n=25" บนเวที** — พูดว่า "n≈40–50 จึงล็อกเป้า 50"
>
> **นี่คือการแก้ "ตัวเลขเหตุผลเชิงออกแบบ (power sim)" ก่อนเห็นข้อมูล — ไม่ใช่การเปลี่ยนสมมติฐาน/เกณฑ์ตัดสิน**
> (PRIMARY §5, วิธีวิเคราะห์ §6, เกณฑ์คัดออก §7 **ไม่เปลี่ยนแม้แต่ตัวเดียว**)
> การล็อกที่แท้จริงคือ *outcome + วิธี + เกณฑ์* ซึ่งเรายังไม่แตะ · สถานะข้อมูลยังเป็น **n = 0**
> จึงเป็นไปไม่ได้ที่จะเป็น p-hacking — เราแก้ก่อนมีข้อมูลให้ hack

> **แก้ถ้อยคำ §10 พร้อมกัน:** เดิม §10 เขียนว่า pose.py *"พิสูจน์แล้วว่าทนกล้องเอียง: เอียง 8° → เพี้ยน 2–3°"*

> ตรวจจับใหม่) — fha เปลี่ยน +2.7° · วิธีเทียบกรอบภาพเปลี่ยน +8.8° · **จึงแก้ถ้อยคำเป็น "ทดสอบเบื้องต้น
> (1 ภาพ, หมุนซอฟต์แวร์): วิธีเทียบแกนลำตัวเพี้ยน 2-3° · วิธีเทียบกรอบภาพเพี้ยน 8.8°"** — ยังไม่ใช่การเอียง

## 5. สมมติฐานที่จะทดสอบ

### PRIMARY (มีข้อเดียว)
> **โมเดลรวม (ท่าทางจาก AI + พฤติกรรม) ทำนายระดับอาการ NRS 0–10 ได้ดีกว่าความบังเอิญอย่างมีนัยสำคัญ**

## 6. วิธีวิเคราะห์ (ล็อกทุกขั้นตอน)

1. **หน่วยวิเคราะห์: 1 คน = 1 แถว** (เฉลี่ยมุมจากภาพหลายมุม) — **ห้ามนับ 4 รูป = 4 แถว** (จะได้ n ปลอม)
2. **โมเดล:** Ridge regression, `alpha = 1.0` **ตายตัว**
   > 🚫 **ห้าม GridSearchCV · ห้ามจูนพารามิเตอร์ · ห้ามลองหลาย seed แล้วเลือกอันสวย**
   > ที่ n=50 การลอง 20 ค่าแล้วเลือกอันดีที่สุด **จะเจอผลลวงในข้อมูลขยะได้แน่นอน**
3. **ทุกขั้นตอนที่เรียนรู้จากข้อมูล (StandardScaler) ต้องอยู่ใน `Pipeline` และ fit ใหม่ทุก fold**
   > 🚫 **ห้าม z-score ทั้งก้อนก่อนแบ่งชุดทดสอบ** (= data leakage)
4. **การประเมิน:** RepeatedKFold 5-fold × 20 repeats, seed ล็อกไว้ล่วงหน้า
   รายงาน out-of-fold R² และ Spearman r พร้อม bootstrap 95% CI
   > 🚫 **ห้ามใช้ single train/test split** (ชุดทดสอบ 10 คน = สัญญาณรบกวนล้วน)
5. **Permutation test:** สลับ label แล้ว **รัน cross-validation ทั้งท่อใหม่ทุกรอบ**
   จำนวน repeats ต้อง**เท่ากัน**ทั้งฝั่งค่าจริงและฝั่งเปรียบเทียบ
6. **Baseline ที่ต้องรายงานเสมอ 3 ตัว:**
   - B0: ค่าเฉลี่ย (null model)
   - B1: แบบสอบถามอย่างเดียว
   - B2: **ท่าทางอย่างเดียว** ← *นี่คือสิ่งที่แอปคู่แข่งทุกตัวในตลาดทำ*
   เปรียบเทียบด้วย **CI ของ "ผลต่าง" จาก paired bootstrap** (สุ่มคนซ้ำ) — **ไม่ใช่ดูว่า CI สองอันทับกันไหม**
7. **Sensitivity analysis:** รายงานผลเมื่อตัดคนที่ติดธงแดงออก (เกณฑ์เขียนไว้แล้วใน §7) — ใช้เกณฑ์เดียวกันกับทุกคน **โดยไม่ดูผลลัพธ์ประกอบ**
8. **λ = 0.6 ในสมการความเสี่ยง เป็นค่าที่เราตั้งเอง** → ต้องรายงานผลที่ λ = 0.5 / 0.6 / 0.7 / 1.0 ทุกครั้ง
9. **รันครั้งเดียว รายงานครั้งเดียว** — ไม่รันซ้ำเพื่อหาผลที่สวยกว่า

---

## 7. เกณฑ์คัดออก (เขียนก่อนเห็นข้อมูล)

- ติดธงแดงข้อใดข้อหนึ่งใน 6 ข้อ (ปวดกลางคืน / ไข้+น้ำหนักลด / ชา-อ่อนแรง / เคยบาดเจ็บ / เคยวินิจฉัย / ปวด > 3 เดือน)
  → **ส่งพบแพทย์ ไม่นำเข้าโมเดล**
- ภาพที่มองไม่เห็นจุด หู / ไหล่ / สะโพก ชัดพอ (ค่าความมั่นใจ < 0.5)
- แบบสอบถามตอบไม่ครบในตัวแปรที่ล็อกไว้
- รหัสในภาพไม่ตรงกับรหัสในแบบสอบถาม

## 8. การศึกษาย่อย: ความน่าเชื่อถือของเครื่องมือ (15 คน, 15 นาที)

ถ่ายภาพ → ให้เดินออกไป → **กลับมายืนใหม่** → ถ่ายซ้ำ
(🚫 **ห้ามรันโมเดลซ้ำบนรูปเดิม** — นั่นวัดแค่ความนิ่งของโปรแกรม ไม่ใช่ความนิ่งของการวัด)

**ได้:** ICC(2,1) + SEM + **MDC95** (การเปลี่ยนแปลงขั้นต่ำที่เชื่อได้ว่าเปลี่ยนจริง)

**พูดได้แค่นี้:** *"แอปจะไม่บอกว่าท่าทางคุณเปลี่ยน ถ้าเปลี่ยนน้อยกว่า MDC95"*
🚫 **ห้ามลื่นไปเป็น "มีความหมายทางคลินิก"** (นั่นคือ MCID ซึ่งเราไม่มี)

**ถ้า ICC ของความไม่สมมาตร < 0.6** → **พูดเองบนเวที** และลดสถานะตัวแปรนี้เป็น *"สัญญาณให้ถ่ายซ้ำ/ปรึกษาครูอนามัย"* ไม่ใช่ตัวเลขบนหน้าจอ

## 9. สิ่งที่ระบบยังมีคุณค่า แม้ผลสถิติออกมาเป็น null

*(กำแพงกั้นระหว่าง "คุณค่าของผลิตภัณฑ์" กับ "ค่า p ของโมเดล")*

1. **คัดกรองธงแดง 6 ข้อ → ส่งต่อครูอนามัย** — ฟังก์ชันความปลอดภัย ไม่ต้องพึ่ง p-value
2. **Teacher Dashboard ระดับกลุ่ม** (ไม่ระบุตัวตน, ปิดเซลล์ที่มีคนน้อยกว่า 10) → โรงเรียนจัดคาบยืดเหยียดให้ห้องที่เสี่ยงสูงก่อน
3. **โหมดนักเรียน: ไม่ถามอาการปวดเลย** → ไม่มีปัญหา "ถามคำตอบแล้วทายคำตอบ" ตอนใช้งานจริง
4. **การวัดผลก่อน/หลังท่าบริหาร** — เป็นการทดลองที่ n=25 ก็เพียงพอ
